# Editor1

Editor1 یک محیط تحت وب برای نوشتن و اجرای کدهای HTML، CSS و JavaScript است. محیط شامل ویرایشگر کد و پیش‌نمایش زنده است و برای استفاده در مرورگر دسکتاپ و موبایل طراحی شده است.

## وضعیت پروژه

| بخش | وضعیت مستند |
|---|---|
| محیط اصلی ویرایشگر و پیش‌نمایش زنده | پیاده‌سازی شده |
| تب‌های مستقل HTML، CSS و JavaScript | پیاده‌سازی شده |
| ذخیره خودکار در مرورگر | پیاده‌سازی شده؛ محدود به همان مرورگر و مبدأ |
| چیدمان دسکتاپ و تقسیم‌کننده قابل جابه‌جایی | پیاده‌سازی شده |
| رابط تک‌پنجره‌ای موبایل و کلیدهای کمکی | پیاده‌سازی شده |
| پیشنهادهای HTML، CSS و JavaScript | مسیر انتخاب صفحه‌کلید بر اساس منوی مالک پیشنهاد اصلاح شد تا CSS/JavaScript هرگز از درج تگ HTML استفاده نکنند؛ آزمون خودکار منو و درج متنی CSS اضافه شد؛ کاربر درج صحیح `display` بدون تگ HTML را در نسخه آنلاین تأیید کرد؛ نسخه آفلاین جداگانه هنوز با این اصلاح آزمایش نشده است |

| آزمون داده مرجع کاتالوگ | مرحله ۲-۲ تکمیل؛ ۴۱ آزمون خودکار موفق و تطبیق هر ۳۴۸ رکورد بدون اختلاف |
| بسته مستقل آفلاین | فرایند ساخت و فایل خروجی وجود دارد؛ مسیر New page و نمایش زنده HTML، اعمال CSS و اجرای JavaScript در Preview تأیید شده‌اند؛ آزمون ذخیره‌سازی، سایر قابلیت‌ها و قطع اینترنت هنوز باقی است |
| ارسال ایمیل نسخه آفلاین | workflow دستی وجود دارد؛ ارسال واقعی باید جداگانه تأیید شود |

این جدول وضعیت مستندات و پیاده‌سازی شناخته‌شده را نشان می‌دهد؛ موفقیت CI به‌تنهایی به معنی آزمون واقعی در مرورگر یا دستگاه کاربر نیست.

## معماری مخزن

- `index.html`، `style.css` و `script.js`: پوسته و هماهنگ‌کننده محیط اصلی.
- `core/`: قابلیت‌های مستقل رابط کاربری؛ هر قابلیت در پوشه خودش نگهداری می‌شود.
- `alfacode/`: موتور مستقل ویرایشگر، زبان‌ها، آزمون‌ها و مستند فنی.
- `scripts/`: ابزارهای ساخت بسته آفلاین و ارسال ایمیل.
- `offline/`: خروجی مستقل تولیدشده.
- `.github/workflows/`: آزمون‌ها، ساخت بسته آفلاین و ارسال دستی ایمیل.

### ماژول‌های اصلی رابط

`core/` شامل پوشه‌های `editor`، `preview`، `header`، `workspace-divider`، `mobile-workspace`، `mobile-extra-keys`، `browser-storage`، `clear-tabs`، `project-reset`، `clear-project-cookies`، `tag-suggestions`، `css-suggestions`، `javascript-suggestions`، `completion-catalog` و `new-page-action` است.

هر قابلیت مستقل باید در پوشه خودش نگهداری شود. فایل‌های ریشه نباید محل انباشته‌شدن منطق اختصاصی قابلیت‌ها شوند.

## اجرای پروژه

برای اجرای نسخه توسعه، مخزن را دریافت و با یک سرور محلی ایستا اجرا کنید. به دلیل استفاده از JavaScript modules، اجرای مستقیم `index.html` با نشانی `file://` روش اجرای توسعه نیست.

نمونه با Python:

```bash
python -m http.server 8000
```

سپس نشانی `http://localhost:8000` را در مرورگر باز کنید.

## بسته مستقل آفلاین

فایل `offline/AlfaCode-Offline.html` از سورس پروژه تولید می‌شود. اسکریپت ساخت در `scripts/build-offline.mjs` و فهرست مرکزی ورودی‌های runtime در `scripts/offline-manifest.json` قرار دارند؛ workflow مربوط در `.github/workflows/build-offline.yml` است. Manifest قابلیت‌ها و صفحه‌های فعال را معرفی می‌کند؛ اسکریپت ساخت ارجاع‌های HTML/CSS و گراف importهای JavaScript را بررسی می‌کند و منابع پویا و غیرقابل‌کشف را از `runtimeFiles` می‌گیرد. نقش‌های مونتاژ پوسته، ویرایشگر، پیش‌نمایش و اجزای رابط نیز در بخش `assembly` همین Manifest تعریف شده‌اند و مسیر فایل‌های HTML/CSS/JS و نقطه‌های ورود باندل از آن خوانده می‌شوند. منطق اختصاصی ساخت برخی Web Componentها همچنان در اسکریپت ساخت باقی است. ممیزی منابع runtime وابستگی خارجی شبکه‌ای پیدا نکرد؛ fetchهای باقی‌مانده در کد میزبانی‌شده به فایل‌های محلی اشاره دارند و در بسته مستقل با assetهای جاسازی‌شده یا wrapperهای آفلاین جایگزین می‌شوند. اعتبارسنجی ساخت URLهای شبکه‌ای شامل HTTP/HTTPS، WebSocket، FTP، localhost، IPv4 و نشانی‌های protocol-relative را در منابع متنی runtime شناسایی می‌کند؛ ارجاع‌های خارجی HTML/CSS و importهای خارجی JavaScript نیز بررسی می‌شوند. خروجی نهایی از نظر وجود سندهای توکار editor/preview و CSS/JavaScript درون‌خطی کنترل می‌شود و فایل نهایی پس از نوشتن موفق فایل موقت جایگزین می‌شود. این بررسی ایستا و مبتنی بر اسکن متنی است؛ بنابراین ممکن است URL موجود در comment یا متن نمونه را نیز تشخیص دهد و URLهایی را که در زمان اجرا به‌صورت پویا ساخته می‌شوند از دست بدهد. این بررسی جای آزمون واقعی مرورگر و قطع اینترنت را نمی‌گیرد. مسیر New page (بازشدن کاتالوگ، نمایش فهرست و بازگشت) و نمایش زنده HTML، اعمال CSS و اجرای JavaScript در Preview توسط کاربر بررسی و تأیید شده‌اند؛ آزمون ذخیره‌سازی، سایر قابلیت‌های اصلی و آزمون با شبکه مسدودشده هنوز برای مرحله نهایی باقی است. خروجی نهایی باید مستقل باشد و برای اجرای قابلیت‌های بسته به فایل JavaScript یا CSS خارجی نیاز نداشته باشد.

در بسته مستقل، صفحه کاتالوگ تکمیل خودکار نیز همراه HTML، CSS و گراف importهای JavaScript خود در فایل نهایی جاسازی می‌شود. دکمه `New page` این سند درون‌خطی را از طریق Blob URL در زبانه جدید باز می‌کند؛ بنابراین باز شدن کاتالوگ به مسیرهای نسبی مخزن یا اینترنت وابسته نیست. اعتبارسنجی ساخت، باقی‌ماندن رفتار قدیمی `about:blank` را نیز رد می‌کند.

پس از تغییر سورس، خروجی آفلاین باید از مسیر ساخت مجدداً تولید شود؛ ویرایش دستی خروجی جایگزین اصلاح سورس نیست.

## گردش‌کارهای GitHub

- `alfacode-tests.yml`: بررسی syntax فایل‌های یکپارچه‌سازی و اجرای آزمون‌های خودکار AlfaCode.
- `build-offline.yml`: ساخت خروجی مستقل آفلاین؛ تغییر فایل‌ها در سراسر مخزن trigger را فعال می‌کند، به‌جز Markdown، آزمون‌ها، مثال‌ها و خود فایل خروجی آفلاین. این پوشش عمومی باعث می‌شود فایل runtime جدید در مسیرهای تازه نیز از trigger جا نماند؛ تشخیص منابعی که واقعاً وارد بسته می‌شوند همچنان بر عهده Manifest و اسکریپت ساخت است.
- `send-offline-email.yml`: اجرای دستی ارسال نسخه آفلاین از طریق ایمیل؛ تنظیم Secrets لازم است.

نتیجه هر workflow باید از صفحه Actions مخزن بررسی شود. workflow موفق، آزمون دستی مرورگر و دستگاه را جایگزین نمی‌کند.

## قواعد توسعه پروژه

1. هر قابلیت مستقل باید پوشه جداگانه داشته باشد.
2. در صورت تناسب با نوع قابلیت، فایل‌های HTML، CSS و JavaScript آن در همان پوشه قرار می‌گیرند.
3. منطق اختصاصی قابلیت‌ها در فایل‌های ریشه قرار نگیرد.
4. تغییرات فقط پس از تأیید مدیر پروژه انجام شوند و هر کار به زیرمرحله‌های کوچک تقسیم شود.
5. پیش از تغییر فایل موجود در GitHub، نسخه جاری و SHA آن دریافت شود.
6. پس از هر تغییر کد یا ساختار، این README و README اختصاصی AlfaCode با وضعیت واقعی هماهنگ شوند.
7. هیچ قابلیت یا آزمونی که اجرا نشده، تکمیل‌شده یا موفق اعلام نشود.
8. نسخه آفلاین باید از سورس اصلی تولید شود.
