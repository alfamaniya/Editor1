# قوانین و ساختار پروژه Editor1

## تاریخچه توسعه AlfaCode

موتور AlfaCode به‌صورت ماژولار ساخته و به محیط Editor1 متصل شد. در این مسیر، مدل سند و وضعیت ویرایشگر، انتخاب و مکان‌نما، تراکنش‌های اتمی و تاریخچه Undo/Redo توسعه یافتند؛ سپس ورودی صفحه‌کلید و کلیپ‌بورد، رندر خطوط، مدیریت زبان و تحلیل پایه HTML/CSS/JavaScript، رنگ‌بندی نحوی، شماره خطوط، تطبیق پرانتزها و تم‌های روشن و تاریک اضافه شدند. مجموعه آزمون خودکار پایه و گردش‌کار CI نیز ایجاد شد.

در مرحله یکپارچه‌سازی، موتور به رابط Editor1 و Live Preview متصل شد؛ همگام‌سازی مکان‌نما و انتخاب متن و اسکرول مشترک gutter و ویرایشگر اصلاح شد. در بررسی آفلاین، مسیرهای محلی منابع و شیوه اجرای پروژه با سرور محلی مستند شدند. تاریخچه تفصیلی APIها و اجزای AlfaCode در README اختصاصی آن نگهداری می‌شود.

## نقشه مسیر — پیشنهاد و تکمیل خودکار تگ‌های HTML

این نقشه مسیر محدوده و ترتیب توسعه قابلیت پیشنهاد تگ‌ها را مشخص می‌کند. رفتار اصلی مورد تأیید مدیر پروژه است: پس از پذیرش یک پیشنهاد، سیستم زمینه تازه کد را تحلیل می‌کند و در صورت وجود، پیشنهاد مرتبط بعدی را نمایش می‌دهد؛ از جمله پیشنهاد تگ بسته‌شونده یا تگ‌های قابل استفاده درون عنصر جاری. پیاده‌سازی اولیه موتور، منوی پیشنهاد و اتصال به ویرایشگر آغاز شده است. وضعیت آزمون و انتشار در جدول زیر شفاف نگهداری می‌شود.

### مبنای اولویت‌بندی تگ‌ها

منوی پیشنهاد در هر لحظه حداکثر **۱۰ گزینه** نمایش می‌دهد. ترتیب اولیه بر پایه فراوانی واقعی عناصر در صفحات وب است، نه ترتیب الفبایی. مبنای آماری فعلی، فصل Markup گزارش Web Almanac 2024 از HTTP Archive است؛ این گزارش داده‌های خزش ژوئن ۲۰۲۴ را بررسی کرده و در رتبه‌بندی فراوانی عناصر، ترتیب پرتکرارها را چنین گزارش می‌کند:

| اولویت پایه | تگ | ملاحظه |
|---:|---|---|
| ۱ | `div` | عنصر عمومی بلوکی |
| ۲ | `a` | پیوند |
| ۳ | `span` | عنصر عمومی درون‌خطی |
| ۴ | `li` | عضو فهرست |
| ۵ | `script` | اسکریپت |
| ۶ | `img` | تصویر؛ عنصر void |
| ۷ | `p` | بند |
| ۸ | `link` | فقط در زمینه معتبر، مانند `head` |
| ۹ | `meta` | فقط در زمینه معتبر، مانند `head` |
| ۱۰ | `i` | متن با معنای اصطلاحی/نمایشی مشخص |

**نکته روش‌شناختی:** عنصر `path` در رتبه‌بندی کلی گزارش دیده می‌شود، اما عنصر SVG است، نه تگ HTML معمولی؛ بنابراین در منوی عمومی HTML جایگاه ثابت نمی‌گیرد و باید در زمینه SVG پیشنهاد شود. تگ‌های ساختاری مانند `html`، `head` و `body` نیز با وجود فراوانی بسیار بالای حضور در صفحات، بر اساس زمینه سند و محل مکان‌نما پیشنهاد می‌شوند. آمار فراوانی، اولویت پایه را تعیین می‌کند؛ معتبر بودن تگ در محل فعلی کد بر رتبه آماری مقدم است. اگر تگی از نظر ساختار HTML در آن محل مجاز نباشد، نباید صرفاً به دلیل محبوبیت نمایش داده شود.

منابع بررسی‌شده:
- [HTTP Archive — Web Almanac 2024: Markup](https://almanac.httparchive.org/en/2024/markup)؛ منبع اصلی آمار فراوانی و میزان رواج عناصر.
- [HTTP Archive — Web Almanac 2021: Markup](https://almanac.httparchive.org/en/2021/markup)؛ برای مقایسه روند و ثبات عناصر پرتکرار در سال‌های مختلف.
- [MDN — HTML elements reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements)؛ مرجع دسته‌بندی و کاربرد عناصر HTML.
- [MDN — Void elements](https://developer.mozilla.org/en-US/docs/Glossary/Void_element)؛ مرجع تشخیص عناصر بدون تگ پایانی.

این رتبه‌بندی یک خط مبنای مستند است؛ در زمان پیاده‌سازی، اگر گزارش آماری جدیدتر و قابل اتکایی منتشر شده باشد، داده‌ها دوباره بررسی و تاریخ منبع در README ثبت می‌شود.

**ساختار ماژول رابط:** `core/tag-suggestions/` با سه فایل `tag-suggestions.html`، `tag-suggestions.css` و `tag-suggestions.js`. موتور پیشنهاد و داده‌های زبان در `alfacode/src/` باقی می‌مانند؛ رابط فقط مسئول نمایش و تعامل است.

**قواعد اجرایی:** حداکثر ۱۰ پیشنهاد در منو؛ رتبه‌بندی پایه بر اساس آمار استفاده؛ فیلتر و اعتبارسنجی زمینه پیش از نمایش؛ جداسازی عناصر HTML و SVG؛ و به‌روزرسانی هر دو README در هر تغییر. نسخه آفلاین باید همواره از سورس اصلی بازتولید شود و منطق جداگانه‌ای نداشته باشد.

**جزئیات پیاده‌سازی فعلی:** موتور در `alfacode/src/language/html/html-completion.js` قرار دارد و مستقل از DOM است. رابط سه‌فایلی در `core/tag-suggestions/` قرار گرفته است. در پذیرش تگ معمولی، تگ باز و بسته با هم درج می‌شوند و مکان‌نما بین آن‌ها می‌ایستد؛ برای تگ‌های void مانند `img` فقط تگ باز درج می‌شود. پس از درج تگ جفتی، منوی زنجیره‌ای تا ۱۰ گزینه (حداکثر ۹ تگ فرزند به‌علاوه گزینه رفتن به تگ پایانی) نمایش می‌دهد.

**الهام معماری:** از الگوی عمومی CodeMirror 6 برای جداسازی منبع تکمیل، فیلتر/رتبه‌بندی، نتیجه پیشنهاد و رابط انتخاب الهام گرفته شده است؛ هیچ فایل اجرایی CodeMirror به پروژه اضافه نشده و موتور با API و مدل سند AlfaCode نوشته شده است. [CodeMirror Autocomplete](https://codemirror.net/examples/autocompletion/) · [CodeMirror Completion API](https://codemirror.net/docs/ref/#autocomplete).

**نتیجه بررسی خودکار:** ۲۶ آزمون موتور موفق شده‌اند ([گزارش CI](https://github.com/alfamaniya/Editor1/actions/runs/44155194573)). ساخت نسخه مستقل آفلاین نیز موفق است ([گزارش ساخت](https://github.com/alfamaniya/Editor1/actions/runs/44155194362)) و خروجی `offline/AlfaCode-Offline.html` شامل موتور و منوی پیشنهاد، بدون script یا stylesheet خارجی است. **محدودیت فعلی:** قواعد زمینه‌ای در این نسخه مجموعه‌ای از قواعد رایج برای `head`، `body`، فهرست‌ها، جدول، فرم، پاراگراف و SVG هستند؛ این نسخه هنوز پیاده‌سازی کامل الگوریتم content model استاندارد WHATWG نیست. آزمون واقعی مرورگر، IME فارسی و رفتار لمس روی دستگاه کاربر هنوز انجام نشده‌اند.

## قوانین اصلی پروژه

1. فایل‌های ریشه شامل `index.html`، `style.css` و `script.js` هسته مرکزی پروژه هستند.
2. هر بخش مستقل باید پوشه اختصاصی با نام مرتبط در مسیر `core/` داشته باشد.
3. هر بخش باید دقیقاً سه فایل اصلی داشته باشد: HTML، CSS و JavaScript.
4. کدهای اختصاصی هر بخش باید فقط در پوشه همان بخش قرار بگیرند.
5. فایل‌های ریشه مسئول چیدمان کلی و اتصال بخش‌ها هستند؛ منطق اختصاصی بخش‌ها نباید به فایل‌های ریشه منتقل شود.
6. زبان README فارسی است؛ اما تمام متن‌های رابط کاربری، نام‌گذاری‌ها، شناسه‌ها و توضیحات داخل کد باید انگلیسی باشند.
7. در هر تغییر ساختاری یا عملکردی، این فایل و README اختصاصی AlfaCode باید متناسب با وضعیت واقعی پروژه به‌روزرسانی شوند.
8. ساختار بخش‌ها باید مستقل و قابل توسعه باقی بماند.
9. قابلیت جدید فقط با درخواست صریح مدیر پروژه پیاده‌سازی می‌شود.

## نوار کلیدهای اضافی موبایل

قابلیت نوار کلیدهای کمکی در پوشه مستقل `core/mobile-extra-keys/` نگهداری می‌شود و فقط در نمایشگرهای موبایل، هنگام فوکوس و بازبودن صفحه‌کلید مجازی نمایش داده می‌شود. این ماژول در سند اصلی میزبان (بیرون از iframe ویرایشگر) قرار دارد تا تغییرات viewport واقعی دستگاه را دریافت کند. دو ردیف قابل پیمایش دارد: ردیف مشترک شامل Tab، کلیدهای جهت‌دار و Backspace؛ و ردیف اختصاصی که با تب فعال HTML، CSS یا JavaScript تغییر می‌کند.

کلیدهای درج متن از طریق رویداد اختصاصی به اتصال ویرایشگر ارسال می‌شوند و تغییر سند با تراکنش‌های موتور AlfaCode انجام می‌شود؛ بنابراین رابط کمکی مستقیماً DOM متن را دست‌کاری نمی‌کند. جفت‌گذاری خودکار پرانتزها، براکت‌ها و آکولادها و نقل‌قول‌ها نیز در همین مسیر انجام می‌شود. کلیدهای حرکتی و Tab از مسیر ورودی موجود ویرایشگر عبور می‌کنند.

وضعیت فوکوس و زبان فعال از iframe ویرایشگر به صفحه میزبان پیام داده می‌شود؛ تشخیص بازشدن کیبورد با `visualViewport` صفحه اصلی انجام می‌شود تا به محدودیت viewport داخل iframe وابسته نباشد. نمایش نوار به تشخیص رابط لمسی یا عرض موبایل، فوکوس ویرایشگر و کاهش ارتفاع viewport در اثر بازشدن کیبورد وابسته است؛ بنابراین حالت Desktop site مرورگر موبایل نیز پشتیبانی می‌شود. تشخیص و اندازه‌گیری دقیق صفحه‌کلید مجازی بین مرورگرها و صفحه‌کلیدهای اندروید تفاوت دارد؛ بنابراین رفتار نهایی، به‌ویژه هنگام تغییر اندازه viewport، باید روی دستگاه واقعی بررسی شود.

نسخه آفلاین نیز فایل‌های HTML/CSS ماژول را در میزبان جاسازی و همان JavaScript را bundle می‌کند؛ منطق جداگانه‌ای برای این قابلیت ندارد.

## معرفی پروژه

Editor1 یک پروژه ماژولار برای توسعه محیط ویرایش کد است. در ساختار فعلی، صفحه اصلی شامل دو بخش ظاهری Editor و Live Preview است.

پوشه `alfacode/` محل توسعه موتور ویرایشگر کد اختصاصی AlfaCode است؛ موتوری مستقل و ماژولار با الهام از معماری و قابلیت‌های ویرایشگرهایی مانند Monaco و CodeMirror.

نسخه اولیه AlfaCode برای شناخت و پشتیبانی از HTML، CSS و JavaScript طراحی می‌شود. معماری باید امکان افزودن زبان‌های دیگر را بدون بازنویسی هسته فراهم کند. توسعه با اولویت اجرای محلی و آفلاین انجام خواهد شد.

## مسئولیت بخش‌های اصلی AlfaCode

- `src/core/`: مدیریت وضعیت ویرایشگر، سند، انتخاب متن، تراکنش‌ها و تاریخچه.
- `src/rendering/`: نمایش محیط ویرایش، خطوط و مکان‌نما.
- `src/input/`: دریافت ورودی صفحه‌کلید و مدیریت کلیپ‌بورد.
- `src/language/`: مدیریت زبان‌ها، توکن‌سازی و هماهنگی تحلیلگرها.
- `src/language/html/`: قواعد و تحلیل ساختار HTML.
- `src/language/css/`: قواعد و تحلیل ساختار CSS.
- `src/language/javascript/`: قواعد و تحلیل ساختار JavaScript.
- `src/features/`: امکانات مستقل مانند شماره خطوط، رنگ‌بندی نحوی و تطبیق پرانتزها.
- `src/themes/`: مدیریت تم‌های روشن و تاریک.
- `src/utils/`: ابزارهای عمومی مشترک.
- `tests/`: محل آزمون‌های خودکار.
- `examples/`: نمونه‌های استفاده از موتور.

## وضعیت پیاده‌سازی

AlfaCode به محیط Editor1 متصل است و قابلیت‌های پایه ویرایش، رنگ‌بندی نحوی، شماره خطوط، تطبیق پرانتزها و انتقال تغییرات به Live Preview را فراهم می‌کند. فایل‌های موردنیاز پروژه به‌صورت محلی نگهداری می‌شوند و اجرای آفلاین از طریق سرور محلی امکان‌پذیر است.

## اجرای پروژه

برای اجرای نسخه یکپارچه و آفلاین، در ریشه مخزن یک سرور محلی اجرا کنید؛ برای نمونه در ویندوز با Python:

```powershell
py -m http.server 8000
```

سپس نشانی `http://localhost:8000` را در مرورگر باز کنید. این سرور فقط فایل‌های همین پوشه را روی رایانه ارائه می‌کند و به اینترنت نیاز ندارد. استفاده از سرور محلی ضروری است؛ بارگذاری مستقیم `index.html` با نشانی `file://` ممکن است به‌دلیل محدودیت امنیتی مرورگر در بارگذاری ES Modules شکست بخورد. پس از بازشدن برنامه می‌توان اتصال اینترنت را قطع کرد؛ همه فایل‌های اجرایی و stylesheetهای پروژه محلی هستند.


## رنگ‌بندی نحوی (Syntax Highlighting)

ماژول رنگ‌بندی نحوی در مسیر `alfacode/src/features/syntax-highlighting/highlighter.js` پیاده‌سازی می‌کند. این ماژول متن را تحلیل نمی‌کند؛ توکن‌های تولیدشده توسط زبان فعال را دریافت می‌کند و آن‌ها را به گره‌های DOM دارای کلاس‌های معنایی تبدیل می‌کند.

- کلاس `SyntaxHighlighter` با متد `render(sourceText, tokens, ownerDocument)` یک `DocumentFragment` می‌سازد.
- متد `renderInto(container, sourceText, tokens)` محتوای نمایشی یک container را با نسخه رنگ‌بندی‌شده جایگزین می‌کند.
- تابع `highlightTokens(sourceText, tokens, ownerDocument, options)` برای استفاده مستقیم در دسترس است.
- نگاشت مشترک انواع توکن HTML، CSS و JavaScript به گروه‌های معنایی مانند `keyword`، `tag`، `attribute`، `string`، `number`، `comment`، `operator` و `punctuation` انجام می‌شود.
- کلاس‌های تولیدشده با پیشوند پیش‌فرض `alfacode-token` ساخته می‌شوند؛ برای نمونه `alfacode-token--keyword` و `alfacode-token--comment`. نوع دقیق توکن نیز در کلاس و ویژگی `data-token-type` حفظ می‌شود.
- فاصله‌ها و بخش‌های بدون توکن با text node نگهداری می‌شوند تا متن منبع بدون حذف یا جابه‌جایی باقی بماند.
- محتوای کد فقط با `createTextNode` و `textContent` وارد DOM می‌شود؛ از `innerHTML` استفاده نمی‌شود.
- ورودی CRLF و CR به LF نرمال می‌شود و موقعیت‌ها مطابق قرارداد UTF-16، صفرمبنا و با انتهای غیرشامل هستند. توکن‌های نامعتبر، خارج از محدوده، نامرتب یا هم‌پوشان رد می‌شوند.
- این ماژول کلاس‌های معنایی را تولید می‌کند؛ تعریف رنگ‌های واقعی و قواعد CSS تم‌ها در مدیریت تم‌ها انجام شده است. اتصال خودکار highlighter به چرخه ویرایش و آزمون مرورگر نیز در مراحل یکپارچه‌سازی و آزمایش بررسی می‌شود.
- بازبینی ایستا انجام شده است؛ آزمون کامل مرورگر هنوز اجرا نشده است.


## شماره خطوط و تطبیق پرانتزها

ماژول شماره خطوط و تطبیق پرانتزها دو قابلیت مستقل در مسیر `alfacode/src/features/` اضافه می‌کند. این قابلیت‌ها در یکپارچه‌سازی با رابط Editor1 به چرخه نمایش EditorView متصل شده‌اند.

### شماره خطوط

فایل `src/features/line-numbers/line-numbers.js` شامل کلاس `LineNumbers` است:

- `new LineNumbers(options)` برای تنظیم کلاس‌های CSS و برچسب دسترس‌پذیری.
- `render(documentModel, ownerDocument, activeLine)` یک عنصر gutter شامل شماره‌های ۱ تا تعداد خطوط سند می‌سازد.
- `renderInto(container, documentModel, activeLine)` محتوای container را با gutter تولیدشده جایگزین می‌کند.
- تعداد خطوط مستقیماً از `Document.getLineCount()` خوانده می‌شود؛ سند خالی نیز یک خط دارد.
- شماره‌ها با `data-line-number` مشخص می‌شوند و خط فعال اختیاری با کلاس و ویژگی داده‌ای جداگانه علامت‌گذاری می‌شود.
- ساختار و کلاس‌های معنایی تولید می‌شوند؛ اندازه، فاصله و رنگ در CSS تم‌ها تعریف خواهند شد.

### تطبیق پرانتزها

فایل `src/features/bracket-matching/bracket-matcher.js` شامل کلاس `BracketMatcher` است:

- `isBracket(character)` بررسی می‌کند که کاراکتر یکی از `()`، `[]` یا `{}` باشد.
- `findAll(sourceText, tokens)` تمام جفت‌های معتبر را با موقعیت باز و بسته برمی‌گرداند.
- `findMatch(sourceText, cursorOffset, tokens)` جفت مرتبط با کاراکتر زیر مکان‌نما یا کاراکتر بلافاصله پیش از آن را پیدا می‌کند؛ در صورت نبود جفت معتبر `null` برمی‌گرداند.
- الگوریتم از پشته برای مدیریت جفت‌های تو در تو استفاده می‌کند.
- در صورت ارائه توکن‌ها، محدوده رشته‌ها، templateها، regexها، کامنت‌ها، متن HTML، مقدار ویژگی‌ها و doctype از جست‌وجو کنار گذاشته می‌شوند تا براکت‌های داخل آن‌ها به‌عنوان ساختار کد تفسیر نشوند.
- توکن‌های ورودی باید مرتب، معتبر و بدون هم‌پوشانی باشند. موقعیت‌ها صفرمبنا و بر اساس UTF-16 هستند.
- فقط جفت‌های کامل و درست‌تودرتو گزارش می‌شوند؛ علامت‌گذاری بصری جفت‌ها و اتصال به مکان‌نما در یکپارچه‌سازی با رابط Editor1 انجام شده است.

### وضعیت بررسی

بازبینی ایستا و تطبیق APIها با مدل سند و قرارداد توکن‌ها انجام شده است. آزمون‌های پایه موتور در آزمون‌های پایه موفق بوده‌اند و اتصال قابلیت‌ها به DOM در یکپارچه‌سازی با رابط Editor1 انجام شده است.


## مدیریت تم‌های روشن و تاریک (Themes)

مدیریت تم‌ها مدیریت تم و استایل‌های پایه روشن و تاریک را در مسیر `alfacode/src/themes/` اضافه می‌کند. این مرحله ظاهر پایه ویرایشگر و رنگ‌بندی توکن‌های HTML، CSS و JavaScript را از طریق CSS custom properties فراهم می‌کند؛ هنوز اتصال نهایی این تم‌ها به صفحه اصلی Editor1 در این مرحله انجام نشده است.

### ThemeManager

فایل `src/themes/theme-manager.js` شامل کلاس `ThemeManager` است:

- `new ThemeManager(options)` دو تم پیش‌فرض `dark` و `light` را ثبت می‌کند و به‌صورت پیش‌فرض تم `dark` را فعال می‌کند.
- گزینه‌های سازنده: `defaultTheme`، `rootElement` و `themes` برای تعیین تم آغازین، عنصر ریشه اختیاری و ثبت تم‌های افزوده.
- `register(theme)` تمی با شناسه یکتا و کلاس CSS معتبر ثبت می‌کند. شیء تم شامل `id` و گزینه‌های `label` و `className` است.
- `get(id)`، `has(id)` و `list()` برای دریافت و فهرست تم‌ها هستند.
- `setTheme(id, rootElement)` تم فعال را تغییر می‌دهد و در صورت ارائه عنصر DOM، کلاس تم را روی آن اعمال می‌کند.
- `apply(rootElement)` تم فعال را روی یک عنصر DOM اعمال می‌کند.
- `unregister(id)` تم غیرفعال را حذف می‌کند؛ حذف تم فعال مجاز نیست.
- `clear(rootElement)` کلاس و ویژگی تم را از عنصر ریشه پاک می‌کند و وضعیت فعال را بازنشانی می‌کند.
- این ماژول به `document` سراسری یا API شبکه وابسته نیست؛ عنصر DOM فقط از طریق آرگومان صریح دریافت می‌شود.

### فایل‌های CSS و قرارداد ظاهر

- `src/themes/dark.css`: پالت تیره و مقادیر متغیرهای CSS تم تاریک.
- `src/themes/light.css`: پالت روشن و مقادیر متغیرهای CSS تم روشن.
- `ThemeManager` فقط کلاس `alfacode-theme-dark` یا `alfacode-theme-light` و ویژگی `data-alfacode-theme` را روی ریشه اعمال می‌کند؛ بارگذاری فایل‌های CSS باید به‌صورت محلی توسط مصرف‌کننده پروژه انجام شود.
- متغیرهای مشترک با پیشوند `--alfacode-` تعریف شده‌اند و سطح پس‌زمینه، متن، انتخاب، مکان‌نما، شماره خطوط، تطبیق پرانتزها و رنگ گروه‌های معنایی توکن‌ها را پوشش می‌دهند.
- کلاس‌های رنگ‌بندی با خروجی واقعی `SyntaxHighlighter` هماهنگ‌اند؛ از جمله `alfacode-token--keyword`، `alfacode-token--tag`، `alfacode-token--string`، `alfacode-token--comment` و `alfacode-token--invalid`.
- کلاس‌های `alfacode-editor-view`، `alfacode-line`، `alfacode-line-content`، `alfacode-selection`، `alfacode-cursor` و کلاس‌های شماره خطوط با اجزای موجود هماهنگ شده‌اند.
- کلاس CSS عمومی `alfacode-bracket-match` برای نمایش جفت پرانتز در یکپارچه‌سازی با رابط Editor1 به چرخه رندر متصل شده است.

### وضعیت بررسی

فایل‌های ThemeManager و دو stylesheet از نظر ساختار، اعتبارسنجی ورودی‌ها و تطبیق نام کلاس‌ها با ماژول‌های موجود بازبینی ایستا شده‌اند. آزمون اجرایی و بررسی واقعی ظاهر در مرورگر هنوز انجام نشده است و در آزمون‌های پایه و یکپارچه‌سازی بعدی بررسی خواهد شد.


## آزمون‌های پایه — آزمون اجزا و تعامل ماژول‌ها

آزمون‌های پایه آغاز شده است. مجموعه آزمون خودکار اولیه در `alfacode/tests/alfacode.test.mjs` ایجاد شده و گردش‌کار GitHub Actions در `.github/workflows/alfacode-tests.yml` برای اجرای آن روی تغییرات مرتبط تنظیم شده است.

آزمون‌های فعلی مدل سند و offsetهای UTF-16، انتخاب متن، تراکنش اتمی، تاریخچه Undo/Redo، هماهنگی Editor، ورودی صفحه‌کلید و چرخه اتصال InputController، ثبت زبان‌ها، اعتبارسنجی توکن‌ها، ParserManager، تحلیل نمونه HTML/CSS/JavaScript، تطبیق پرانتزها و مدیریت تم‌ها را پوشش می‌دهند.

فرمان اجرای محلی در ریشه مخزن:

```bash
node --experimental-default-type=module --test alfacode/tests/alfacode.test.mjs
```

در نخستین اجرای واقعی GitHub Actions، ۱۷ آزمون از ۱۸ آزمون موفق شدند و آزمون جفت‌سازی براکت‌های متقاطع (`([)]`) شکست خورد. منطق `BracketMatcher` اصلاح شد تا با مشاهده بستار ناسازگار، پشته بازکننده‌های معلق را باطل کند. اجرای مجدد GitHub Actions روی commit اصلاحی با موفقیت پایان یافت: هر ۱۸ آزمون موفق و صفر آزمون ناموفق بود. بنابراین آزمون‌های خودکار پایه آزمون‌های پایه تأیید شده‌اند. آزمون DOM واقعی مرورگر، IME فارسی، کارایی اسناد بزرگ و رفتار کامل رندر همچنان به بررسی تکمیلی نیاز دارند.


## تکمیل یکپارچه‌سازی AlfaCode — یکپارچه‌سازی با رابط Editor1

یکپارچه‌سازی با رابط Editor1 تکمیل شده است. موتور اختصاصی از طریق ماژول‌های ES به بخش Editor متصل است و مرزبندی مسئولیت‌ها حفظ شده است:

- `core/editor/`: ساخت نمونه `Editor`، نمایش `EditorView`، دریافت ورودی با `InputController` و مدیریت زبان‌های HTML، CSS و JavaScript.
- `script.js`: هماهنگ‌کننده اصلی میان iframe ویرایشگر و iframe پیش‌نمایش؛ پیام تغییر کد را اعتبارسنجی و آخرین خروجی را تا آماده‌شدن Preview نگهداری می‌کند.
- `core/preview/`: نمایش HTML، CSS و JavaScript در iframe مستقل با `sandbox="allow-scripts"` و بدون مجوز `allow-same-origin`.
- `SyntaxHighlighter`، `LineNumbers` و `BracketMatcher` به چرخه رندر متصل‌اند.
- انتخاب متن و مکان‌نما میان DOM مرورگر و مدل سند همگام می‌شوند؛ ورودی و حذف محدوده انتخاب‌شده نیز در بررسی دستی کاربر تأیید شده‌اند.
- gutter و متن کد از میزبان اسکرول مشترک استفاده می‌کنند و معیار ارتفاع خطوط در CSS هماهنگ شده است.
- ورودی در حال composition باعث رندر زودهنگام نمی‌شود و متن نهایی در پایان composition به سند منتقل می‌شود.

آزمون‌های خودکار موتور و بررسی نحوی فایل‌های اتصال در GitHub Actions موفق بوده‌اند؛ هر ۱۸ آزمون پایه با صفر خطا اجرا شده‌اند. [گزارش CI](https://github.com/alfamaniya/Editor1/actions/runs/44090566282). رفتار پایه مکان‌نما، جابه‌جایی و حذف انتخاب نیز توسط کاربر در نسخه منتشرشده بررسی شده است. آزمون اختصاصی IME فارسی روی دستگاه واقعی در این محیط قابل شبیه‌سازی نیست و به‌عنوان بررسی تکمیلی دستگاه ثبت می‌شود؛ این مورد مانع تکمیل اتصال پایه یکپارچه‌سازی با رابط Editor1 نیست.

## تکمیل بررسی اجرای آفلاین — ممیزی اجرای آفلاین

ممیزی اجرای آفلاین از نظر ساختار منابع، وابستگی‌ها، اجرای محلی و گردش‌کار انتشار تکمیل شده است:

- صفحه اصلی فقط فایل‌های محلی `style.css` و `script.js` را بارگذاری می‌کند.
- صفحه Editor فایل‌های CSS محلی، stylesheetهای تم محلی و ماژول‌های AlfaCode با مسیرهای نسبی را بارگذاری می‌کند.
- صفحه Preview و هماهنگ‌کننده اصلی نیز فایل‌های محلی هستند؛ خروجی کاربر در iframe دارای sandbox اجرا می‌شود.
- در فایل‌های اجرایی و stylesheetهای بررسی‌شده، ارجاع ضروری به CDN، کتابخانه خارجی، فونت شبکه‌ای یا سرویس راه دور وجود ندارد.
- اجرای آفلاین باید از طریق سرور محلی انجام شود تا محدودیت مرورگر برای ES Modules در `file://` ایجاد نشود؛ راه‌اندازی سرور به اینترنت وابسته نیست.
- آزمون نحوی JavaScript، ۱۸ آزمون پایه AlfaCode و ساخت و انتشار GitHub Pages موفق بوده‌اند. [گزارش ساخت و انتشار Pages](https://github.com/alfamaniya/Editor1/actions/runs/44090603909).

**نتیجه:** توسعه و یکپارچه‌سازی اولیه AlfaCode تکمیل شده است. آزمون دستی IME فارسی و سنجش کارایی روی فایل‌های بسیار بزرگ، ارزیابی‌های تکمیلی برای دستگاه و مرورگر واقعی هستند و به‌عنوان نقص پنهان یا آزمون انجام‌شده گزارش نمی‌شوند.


## رابط کاربری جدید Editor1

چیدمان صفحه اصلی شامل یک هدر سراسری و دو پنل کنار هم است. هر قابلیت مستقل در پوشه اختصاصی خود قرار دارد:

- هدر اصلی در `core/header/` و تقسیم‌کننده قابل جابه‌جایی در `core/workspace-divider/` قرار دارند؛ هرکدام دقیقاً سه فایل HTML، CSS و JavaScript دارند.
- هدر تمام عرض صفحه را می‌گیرد و محتوای آن در نمایشگرهای باریک به‌صورت افقی قابل پیمایش است.
- پنل ویرایشگر در سمت چپ و پنل خروجی زنده در سمت راست قرار دارند.
- تقسیم‌کننده با ماوس، لمس و کلیدهای جهت‌دار قابل جابه‌جایی است.
- پنل خروجی فقط محتوای پیش‌نمایش را نشان می‌دهد و هدر یا نوار ابزار داخلی ندارد.
- ویرایشگر سه تب مستقل HTML، CSS و JavaScript دارد و محتوای هر تب هنگام جابه‌جایی حفظ می‌شود.
- پیش‌نمایش، محتوای سه تب را با هم ترکیب می‌کند تا CSS روی HTML اعمال شود و JavaScript در همان خروجی اجرا شود.
- فایل‌های ریشه فقط چیدمان و هماهنگی کلی را انجام می‌دهند؛ منطق اختصاصی هدر و تقسیم‌کننده در پوشه‌های خودشان باقی می‌ماند.
- گردش‌کار CI بررسی نحوی فایل‌های ویرایشگر، پیش‌نمایش، هدر، تقسیم‌کننده و هماهنگ‌کننده اصلی را انجام می‌دهد.

- اجرای دستی نیز از بخش **Actions → Build AlfaCode Offline → Run workflow** در GitHub امکان‌پذیر است.
- ماژول‌های ES موتور با نسخه ثابت esbuild در زمان ساخت bundle می‌شوند؛ CSS و JavaScript رابط، هدر، تقسیم‌کننده و Preview نیز در HTML نهایی جای‌گذاری می‌شوند.
- خروجی نهایی به فایل‌های جانبی، CDN، سرور محلی یا اتصال اینترنت در زمان اجرا وابسته نیست و برای اجرا باید فایل HTML را در مرورگر باز کرد.
- فایل‌های مستندات و آزمون‌ها در خروجی اجرایی وارد نمی‌شوند.
- ساخت، ارجاعات خارجی و وجود بخش‌های اصلی سند را اعتبارسنجی می‌کند. گزارش تعداد فایل‌های ورودی و حجم منبع و خروجی در گزارش اجرای GitHub Actions ثبت می‌شود.
- در پایان ساخت، فایل خروجی در پوشه `offline/` به شاخه `main` commit می‌شود. commit خروجی به‌تنهایی باعث اجرای دوباره این گردش‌کار نمی‌شود.

**محدوده تأیید:** ساخت و اعتبارسنجی خودکار فایل به‌وسیله workflow انجام می‌شود. اجرای واقعی فایل تولیدشده با دوبار کلیک در مرورگرهای مقصد باید پس از اولین خروجی نیز به‌صورت دستی بررسی شود؛ تا پیش از آن، سازگاری مرورگر به‌عنوان آزمون عملی تأییدشده گزارش نمی‌شود.


## ارسال نسخه آفلاین به ایمیل شرکت

گردش‌کار دستی `.github/workflows/send-offline-email.yml` آخرین نسخه `offline/AlfaCode-Offline.html` را از مخزن می‌خواند و محتوای آن را از طریق Gmail به نشانی `a.mamghanian@isaco.ir` ارسال می‌کند.

- اجرا فقط با انتخاب دستی گردش‌کار **Send AlfaCode Offline by Gmail** از زبانه Actions انجام می‌شود؛ با push یا تغییر فایل‌ها ایمیلی ارسال نمی‌شود.
- اسکریپت `scripts/send-offline-email.py` محتوای UTF-8 فایل را اعتبارسنجی می‌کند و کل آن را بدون تقسیم‌بندی و بدون ضمیمه، در بدنه یک ایمیل متنی با موضوع `AlfaCode Offline` قرار می‌دهد.
- کل متن فایل در یک پیام و از طریق اتصال امن TLS به سرور SMTP گوگل ارسال می‌شود. هیچ عنوان، شماره بخش یا متن توضیحی به محتوای کد اضافه نمی‌شود.
- برای فعال‌سازی، در تنظیمات مخزن به مسیر **Settings → Secrets and variables → Actions → New repository secret** بروید و دو Secret زیر را بسازید:
  - `GMAIL_USERNAME`: آدرس کامل حساب Gmail فرستنده.
  - `GMAIL_APP_PASSWORD`: رمز اختصاصی برنامه گوگل (App Password)، نه رمز اصلی حساب.
- ایجاد App Password در حساب گوگل به فعال بودن تأیید دومرحله‌ای (2-Step Verification) نیاز دارد. این رمز را فقط در GitHub Secrets وارد کنید و آن را در کد، README یا پیام‌ها قرار ندهید.
- برای ارسال، از مسیر **Actions → Send AlfaCode Offline by Gmail → Run workflow** گردش‌کار را اجرا کنید. نتیجه و تعداد ایمیل‌های ارسال‌شده در گزارش اجرا ثبت می‌شود.
- این گردش‌کار فقط مجوز خواندن مخزن دارد و هیچ فایلی را تغییر یا commit نمی‌کند. اگر ارسال در میانه کار با خطا مواجه شود، اجرای workflow ناموفق اعلام می‌شود؛ ممکن است ایمیل‌های بخش‌های قبلی قبلاً ارسال شده باشند.

## نمونه آغازین ویرایشگر

ویرایشگر با یک نمونه کامل و هماهنگ در هر سه تب باز می‌شود. تب HTML ساختار صفحه نمونه را نگه می‌دارد، تب CSS ظاهر کارت و اجزای آن را تعریف می‌کند و تب JavaScript رفتار دکمه شمارنده را پیاده‌سازی می‌کند. هیچ‌کدام از استایل‌ها یا کدهای رفتاری نمونه داخل HTML قرار نگرفته‌اند؛ هر زبان در بافر مستقل خودش نگهداری می‌شود.

با جابه‌جایی میان تب‌ها، محتوای هر زبان حفظ می‌شود. Live Preview نیز سه منبع HTML، CSS و JavaScript را با هم ترکیب می‌کند؛ بنابراین تغییر استایل یا رفتار، بدون نیاز به انتقال کد به تب HTML در خروجی قابل مشاهده است.


## ذخیره‌سازی خودکار در مرورگر

کدهای سه تب HTML، CSS و JavaScript به‌صورت خودکار و با تأخیر کوتاه در `localStorage` مرورگر ذخیره می‌شوند. با بارگذاری دوباره صفحه، آخرین نسخه معتبر هر سه منبع بازیابی می‌شود. وضعیت ذخیره‌سازی در نوار پایین ویرایشگر نمایش داده می‌شود. داده‌ها فقط در همان مرورگر و همان مبدأ (origin) در دسترس‌اند؛ پاک‌کردن داده‌های سایت یا مرورگر می‌تواند آن‌ها را حذف کند. این قابلیت به اینترنت یا سرویس بیرونی وابسته نیست.

منطق ذخیره‌سازی در `core/browser-storage/` مستقل از هسته موتور AlfaCode قرار دارد و فایل مستقل آفلاین نیز از طریق گردش‌کار ساخت پروژه با همین قابلیت تولید می‌شود.


## رابط کاربری موبایل

در نمایشگرهای با عرض حداکثر ۷۰۰ پیکسل، محیط کار به‌صورت تک‌پنجره‌ای نمایش داده می‌شود. کاربر با نوار جابه‌جایی موبایل بین Editor و Preview حرکت می‌کند؛ در این حالت تقسیم‌کننده دو پنل پنهان است و هر بخش تمام فضای کاری را می‌گیرد. در نمایشگرهای بزرگ‌تر، چیدمان دوپنلی و تقسیم‌کننده قابل‌جابه‌جایی بدون تغییر باقی می‌ماند.

- `core/mobile-workspace/`: کنترل مستقل جابه‌جایی بین نمای ویرایشگر و پیش‌نمایش؛ شامل فایل‌های HTML، CSS و JavaScript.
- تب‌های زبان، نوار وضعیت و فضای ویرایش برای لمس و نمایشگر باریک بهینه شده‌اند.
- ارتفاع رابط با visualViewport هماهنگ می‌شود تا هنگام نمایش صفحه‌کلید مجازی، فضای قابل‌استفاده بهتر تنظیم شود.
- گردش‌کار ساخت نسخه آفلاین و بررسی نحوی CI تغییرات این بخش را نیز پوشش می‌دهند.

## بهینه‌سازی واکنش‌گرایی موبایل — اندازه‌های سیال

چیدمان موبایل به‌روزرسانی شده است تا اندازه‌های اجزای اصلی رابط در قواعد موبایل بر پایه درصد فضای در دسترس تعیین شوند، نه مقادیر ثابت پیکسلی. ارتفاع هدر، نوار انتخاب Editor/Preview، تب‌های زبان و نوار وضعیت به‌صورت نسبی تنظیم می‌شوند؛ عرض بخش شماره خطوط و فاصله‌گذاری تب‌ها نیز از درصد استفاده می‌کند. محدودیت حداقل عرض ثابت صفحه حذف شده است تا رابط در عرض‌های باریک نیز امکان تطبیق داشته باشد.

همگام‌سازی ارتفاع با تبدیل ارتفاع `visualViewport` به مقدار پیکسلی از JavaScript حذف شده است؛ ارتفاع سند و بدنه در موبایل از زنجیره ارتفاع ۱۰۰٪ استفاده می‌کند. اسکرول لمسی افقی و عمودی در میزبان ویرایشگر حفظ شده تا خطوط طولانی کد بدون فشرده‌سازی یا شکستن ناخواسته قابل پیمایش باشند.

**محدوده تغییر:** `style.css`، `core/header/header.css`، `core/mobile-workspace/mobile-workspace.css`، `core/mobile-workspace/mobile-workspace.js` و `core/editor/editor.css`. اندازه‌های ثابت نسخه دسکتاپ برای حفظ چیدمان فعلی دسکتاپ دست‌نخورده مانده‌اند؛ قواعد اختصاصی موبایل از اندازه‌های نسبی استفاده می‌کنند.

**محدودیت آزمون:** این تغییر در سورس مخزن ثبت شده است. تا پیش از اجرای تست روی مرورگر و دستگاه واقعی، سازگاری نهایی با تمام اندازه‌های صفحه و رفتار صفحه‌کلید مجازی تأییدشده محسوب نمی‌شود.

## ابزارهای مدیریتی هدر

سه عملیات مدیریتی در هدر قرار گرفته‌اند و هرکدام ماژول مستقل سه‌فایلی خود را دارند:

| عملیات | پوشه | نتیجه |
|---|---|---|
| پاک‌کردن همه تب‌ها | `core/clear-tabs/` | محتوای بافرهای HTML، CSS و JavaScript خالی می‌شود؛ تب‌ها حذف نمی‌شوند. |
| ریست کلی پروژه | `core/project-reset/` | محتوای هر سه تب به نمونه آغازین AlfaCode بازمی‌گردد و ذخیره خودکار مرورگر با نسخه آغازین جایگزین می‌شود. |
| پاک‌کردن کوکی‌ها و داده‌های مرورگر پروژه | `core/clear-project-cookies/` | کوکی‌های قابل دسترس همین مبدأ و کلید ذخیره‌سازی `alfacode.editor1.sources.v1` پاک می‌شوند؛ سپس صفحه دوباره بارگذاری می‌شود. |

هر عملیات پیش از اجرا تأیید کاربر می‌گیرد. پاک‌سازی داده‌ها به مبدأ فعلی پروژه محدود است و از حذف داده‌های سایر وب‌سایت‌ها یا پاک‌کردن کلی `localStorage` مرورگر خودداری می‌کند. به دلیل محدودیت امنیتی مرورگر، کوکی‌های HttpOnly یا کوکی‌هایی که از مسیر/دامنه دیگری قابل دسترس نیستند، از JavaScript قابل حذف یا فهرست‌کردن نیستند.

فرمان‌ها از هدر به هماهنگ‌کننده اصلی و سپس به iframe ویرایشگر ارسال می‌شوند. نسخه مستقل آفلاین نیز همین سه عملیات و پیام‌های تأیید را در فرایند ساخت خود از HTML/CSS ماژول‌ها بازتولید می‌کند.

## اصلاح چیدمان نوار کلیدهای کمکی موبایل

در نسخه جدید، هر دو ردیف نوار کلیدها از شبکه شش‌ستونه با ستون‌های هم‌اندازه استفاده می‌کنند. ردیف علائم زبان فعال در صورت داشتن ۱۲ کلید، به دو ردیف شش‌تایی تقسیم می‌شود؛ در نتیجه هیچ کلیدی از لبه صفحه بیرون نمی‌زند یا به‌صورت ناقص نمایش داده نمی‌شود. عرض هر کلید با عرض صفحه تطبیق می‌یابد و حداقل ارتفاع هدف لمسی ۴۴ پیکسل حفظ می‌شود. این اصلاح در `core/mobile-extra-keys/mobile-extra-keys.css` انجام شده و فایل آفلاین نیز از همین سورس بازتولید می‌شود.

**محدوده آزمون:** اصلاح CSS در سورس ثبت شده است. نمایش نهایی و اندازه لمس کلیدها باید پس از انتشار در مرورگر واقعی موبایل بررسی شود؛ موفقیت ساخت بسته آفلاین به‌تنهایی جایگزین این آزمون دستگاهی نیست.

## اصلاح اسکرول و فضای قابل مشاهده هنگام بازبودن کیبورد موبایل

در بعضی مرورگرهای اندروید، بازشدن صفحه‌کلید مجازی فقط `visualViewport` را کوچک می‌کند و ارتفاع layout viewport را تغییر نمی‌دهد؛ در نتیجه نوار کلیدهای کمکی روی انتهای ویرایشگر می‌افتد و چند خط کد زیر آن پنهان می‌ماند. اکنون ماژول `core/mobile-extra-keys/mobile-extra-keys.js` ارتفاع viewport قابل مشاهده و ارتفاع واقعی نوار کمکی را به پوسته میزبان اعلام می‌کند. `style.css` ارتفاع بدنه را با viewport قابل مشاهده هماهنگ می‌کند و به‌اندازه نوار کلیدها فضای پایین رزرو می‌کند؛ بنابراین iframe ویرایشگر کوچک می‌شود و ناحیه `.editor-host` می‌تواند مستقل از نوار کلیدها اسکرول عمودی و افقی داشته باشد. تغییرات `visualViewport.resize` و `visualViewport.scroll` هر دو پایش می‌شوند.

**محدوده آزمون:** منطق در سورس ثبت شده است؛ اسکرول لمسی در مرورگر واقعی اندروید هنوز باید پس از انتشار بررسی شود. اجرای موفق CI یا ساخت آفلاین به‌تنهایی تأیید رفتار دستگاهی نیست.

## رفع اشکال راه‌اندازی Live Preview در بسته آفلاین

در ساخت بسته مستقل، ابتدا شنونده‌های پیام و رویداد `load` رابط میزبان ثبت می‌شوند و سپس سندهای داخلی Editor و Preview از طریق `srcdoc` بارگذاری می‌شوند. این ترتیب از ازدست‌رفتن رویداد `load` در بارگذاری سریع فایل آفلاین جلوگیری می‌کند؛ در غیر این صورت، میزبان ممکن بود آماده‌شدن Preview را تشخیص ندهد و پیام‌های به‌روزرسانی کد را ارسال نکند. فایل آفلاین باید پس از تغییر سورس با workflow ساخت دوباره تولید شود. موفقیت ساخت، به‌تنهایی جایگزین آزمون اجرای واقعی فایل در مرورگر نیست.

## بررسی عیب‌یابی اجرای مستقیم فایل آفلاین و Live Preview

در ممیزی فایل تولیدشده `offline/AlfaCode-Offline.html`، سند نهایی شامل ۴۵۸ خط و حدود ۲۰۱ کیلوبایت متن بود. کد ویرایشگر و سند Preview با `srcdoc` در همان فایل جاسازی شده‌اند و تگ script یا stylesheet خارجی در خروجی دیده نشد. با این حال، پوسته اولیه هنوز مسیرهای نسبی `src` روی iframeها داشت و بررسی مبدأ پیام‌ها نیز به تطبیق `event.origin` وابسته بود؛ این شرط برای مبدأهای opaque در اجرای `file://` قابل اتکا نیست.

برای رفع این ریسک‌ها، پیام‌های ویرایشگر اکنون با بررسی هویت دقیق `event.source` نسبت به پنجره iframe شناخته‌شده اعتبارسنجی می‌شوند؛ پیام‌های ورودی به ویرایشگر نیز فقط از پنجره والد پذیرفته می‌شوند. اسکریپت ساخت همچنین `src`های نسبی iframe را از خروجی مستقل حذف می‌کند، چون هر دو سند فرزند از طریق `srcdoc` تزریق می‌شوند، و اعتبارسنجی ساخت اکنون باقی‌نماندن `src` روی iframe را نیز کنترل می‌کند. این اصلاح‌ها برای پشتیبانی از اجرای مستقیم فایل محلی هستند؛ آزمون واقعی در مرورگر پس از بازسازی فایل همچنان لازم است.

## واکنش‌گرایی چیدمان دسکتاپ

چیدمان دسکتاپ اکنون از ارتفاع واقعی viewport با `100dvh` (با fallback برابر `100vh`) استفاده می‌کند و زنجیره Flex/Grid برای کوچک و بزرگ شدن پنجره محدودیت‌های حداقل اندازه را رعایت می‌کند. اسکرول ناخواسته در پوسته workspace بسته شده تا ابعاد پنل‌ها از محدوده viewport خارج نشود.

تقسیم‌کننده Editor و Preview نسبت فعلی دو پنل را نگه می‌دارد. ماژول مستقل `core/workspace-divider/workspace-divider.js` با `ResizeObserver` تغییر عرض workspace را تشخیص می‌دهد و همان نسبت را روی عرض تازه اعمال می‌کند؛ محاسبه drag و کلیدهای جهت‌دار نیز بر اساس عرض واقعی قابل مشاهده workspace انجام می‌شود، نه `scrollWidth`. حداقل عرض پنل‌ها به‌صورت تطبیقی تا ۱۸۰ پیکسل محدود می‌شود تا پنجره‌های کوچک‌تر نیز قابل استفاده بمانند.

این اصلاح فقط رفتار دسکتاپ را هدف می‌گیرد و media query و سازوکار تک‌پنجره‌ای موبایل را حفظ می‌کند. ساخت فایل مستقل آفلاین با workflow موجود و بر اساس سورس اصلی انجام می‌شود. رفتار نهایی در مرورگر واقعی و تغییر اندازه زنده پنجره هنوز نیازمند آزمون دستگاهی است.


## اصلاح واکنش‌گرایی دسکتاپ — چیدمان سیال پنل‌ها

ستون‌های Editor و Preview اکنون با واحدهای نسبی CSS Grid (`fr`) اندازه‌گیری می‌شوند، نه عرض‌های ثابت پیکسلی. با کوچک یا بزرگ‌شدن پنجره، هر دو پنل به‌صورت خودکار تمام عرض workspace را پر می‌کنند و نسبت انتخاب‌شده با درگ یا کلیدهای جهت‌دار حفظ می‌شود. حداقل عرض پنل‌ها تا ۱۸۰ پیکسل تطبیقی است و در فضای باریک‌تر کاهش می‌یابد. تغییرات در `core/workspace-divider/workspace-divider.js` و `style.css` اعمال شده‌اند؛ چیدمان موبایل همچنان از قواعد جداگانه خود استفاده می‌کند. نسخه آفلاین از همین سورس بازسازی می‌شود. آزمون واقعی در مرورگر دسکتاپ هنوز باید انجام شود.


## دکمه بازکردن صفحه جدید

یک اکشن مستقل در هدر با شناسه سفارشی `new-page-action` و پوشه `core/new-page-action/` اضافه شده است. این قابلیت سه فایل اختصاصی HTML، CSS و JavaScript دارد. با انتخاب دکمه «New page»، یک برگه خالی جدید مرورگر با مقصد `about:blank` باز می‌شود؛ محتوای آن عمداً خالی نگه داشته شده تا طراحی صفحه در مرحله بعد و با تصمیم مدیر پروژه انجام شود. نسخه آفلاین نیز همین دکمه را در هدر خود ثبت می‌کند.

## صفحه فهرست تکمیل خودکار
- دکمه «New page» در هدر، صفحه مستقل `core/completion-catalog/` را باز می‌کند.
- جدول، پیشنهادهای HTML، CSS و JavaScript را مستقیماً از API کاتالوگ موتورهای تکمیل خودکار دریافت می‌کند؛ فهرست واژه‌ها در صفحه به‌صورت دستی تکرار نشده است.
- دسته‌بندی زبان‌ها، جست‌وجوی متنی و شمارش نتایج در صفحه فراهم است.
- برای افزودن یا اصلاح پیشنهادها، منبع موتور همان زبان در `alfacode/src/language/` تغییر می‌کند و صفحه در بارگذاری بعدی داده‌های جدید را نمایش می‌دهد.
- هر تغییر در کاتالوگ‌های زبان و صفحه مرجع باید خروجی آفلاین را نیز به‌روز کند.

## نقشه مسیر — مدیریت و انتشار کاتالوگ تکمیل خودکار

**تصمیم تأییدشده مدیر پروژه:** صفحه کاتالوگ تکمیل خودکار به مرکز مدیریت پیشنهادهای HTML، CSS و JavaScript توسعه می‌یابد. ورود داده از سه مسیر انجام خواهد شد: ثبت تکی، واردکردن فایل Excel و چسباندن گروهی. همه ورودی‌ها پیش از انتشار در یک جدول قابل بازبینی و ویرایش جمع می‌شوند. انتشار از طریق GitHub API در یک شاخه جداگانه انجام می‌شود؛ سپس Pull Request ساخته می‌شود و فقط پس از بررسی و تأیید مدیر پروژه می‌تواند وارد شاخه `main` شود.

**قاعده اجرای پروژه:** کار به مرحله‌های کوچک و قابل تأیید تقسیم می‌شود. در هر نوبت فقط یک مرحله و زیرمرحله‌های ضروری آن اجرا خواهد شد؛ پس از گزارش نتیجه و بررسی، مرحله بعد آغاز می‌شود. ثبت این نقشه در README به معنی شروع پیاده‌سازی قابلیت‌ها نیست.

### قرارداد اولیه داده

هر رکورد پیشنهاد باید دست‌کم زبان، شناسه پایدار، دسته‌بندی، کلیدواژه، توضیح، متن قابل درج و وضعیت فعال‌بودن را مشخص کند. فیلدهای اختیاری مانند trigger، جزئیات context و رتبه اولویت فقط پس از ممیزی موتورهای فعلی تعریف می‌شوند. JSON باید نسخه schema داشته باشد تا تغییرات آینده قابل مهاجرت و اعتبارسنجی باشند. داده‌های مخصوص هر زبان در بخش مستقل همان زبان نگهداری می‌شوند؛ کاتالوگ صفحه و موتور نباید نسخه‌های جداگانه و ناسازگار از واژه‌ها داشته باشند.

### چرخه انتشار امن

1. صفحه، داده مرجع فعلی را دریافت می‌کند و ورودی‌های جدید را در پیش‌نویس محلی صفحه آماده می‌کند.
2. پیش از ارسال، همه رکوردها اعتبارسنجی می‌شوند؛ موارد تکراری، فیلدهای ناقص و خطاهای قالب باید روشن و قابل اصلاح باشند.
3. کاربر جدول نهایی را بازبینی می‌کند و با اقدام صریح انتشار را آغاز می‌کند.
4. توکن Fine-grained شخصی GitHub فقط هنگام ارسال دریافت می‌شود، در حافظه موقت همان صفحه می‌ماند و هرگز در `localStorage`، فایل‌ها، JSON یا گزارش‌ها ذخیره نمی‌شود. مجوزهای حداقلی لازم برای محتوای مخزن و Pull Request بررسی و مستند خواهند شد.
5. با API، شاخه‌ای جدا از آخرین `main` ساخته می‌شود و فایل JSON در آن ثبت یا به‌روزرسانی می‌شود؛ سپس Pull Request به `main` ایجاد می‌شود. در صورت تغییر هم‌زمان فایل مرجع، ارسال باید متوقف و داده تازه دریافت شود؛ بازنویسی بی‌صدای تغییرات دیگران مجاز نیست.
6. GitHub Actions روی Pull Request اعتبارسنجی JSON و آزمون‌های مرتبط را اجرا می‌کند. نتیجه ناموفق مانع ادغام خواهد بود.
7. مدیر پروژه تغییرات و نتیجه بررسی را در GitHub می‌بیند و خودش درباره Merge تصمیم می‌گیرد؛ ادغام خودکار یا دورزدن Pull Request در این طرح وجود ندارد.
8. پس از Merge، گردش‌کارهای موجود پروژه برای آزمون، انتشار صفحه و بازسازی نسخه آفلاین اجرا می‌شوند. وضعیت هر گردش‌کار جداگانه بررسی و گزارش می‌شود.

### قواعد کنترل تغییر و توقف

- در هر نوبت فقط زیرمرحله جاری اجرا می‌شود؛ شروع زیرمرحله بعد منوط به گزارش نتیجه و تأیید مدیر پروژه است.
- قبل از هر تغییر در فایل موجود، نسخه و SHA فعلی از GitHub دریافت می‌شود؛ تغییرات هم‌زمان نباید بازنویسی شوند.
- ابتدا داده‌های فعلی موتور ممیزی می‌شوند؛ انتقال به JSON نباید باعث حذف پیشنهادها، تغییر ترتیب، از دست‌رفتن منطق context یا تغییر ناخواسته رفتار ویرایشگر شود.
- فایل JSON منبع داده است، نه محل اجرای کد؛ متن‌های واردشده باید به‌عنوان داده بی‌اعتماد اعتبارسنجی و در رابط با روش امن نمایش داده شوند.
- توکن GitHub نباید در مرورگر ذخیره دائمی شود یا در خطاها و گزارش‌ها افشا شود. اگر مجوز امن و حداقلی قابل استفاده نباشد، ارسال متوقف می‌شود و راهکار جایگزین بررسی خواهد شد.
- Pull Request فقط پس از اعتبارسنجی موفق قابل بررسی برای Merge است؛ Merge همواره تصمیم صریح مدیر پروژه باقی می‌ماند.
- هر تغییر واقعی در کد، ساختار یا گردش‌کار باید README اصلی و README اختصاصی AlfaCode را همگام کند.
- هیچ مرحله‌ای صرفاً به دلیل موفقیت CI، آزمون واقعی مرورگر یا دستگاه تلقی نمی‌شود.


### گزارش ممیزی مرحله ۱-۱ — منابع واقعی پیشنهادهای فعلی

این ممیزی فقط فایل‌های موجود را خوانده است؛ هیچ منطق یا داده‌ای در موتورهای فعلی تغییر نکرده است.

| زبان | فایل منبع | محل داده‌ها و API کاتالوگ | آنچه موتور واقعاً پیشنهاد می‌دهد |
|---|---|---|---|
| HTML | `alfacode/src/language/html/html-completion.js` | `HTML_TAG_CATALOG`، `SVG_TAGS` و `CONTEXT_TAGS`؛ خروجی `getHTMLCompletionCatalog()` | تگ‌های باز، تگ‌های بسته‌شونده، عناصر وابسته به زمینه، SVG، تگ‌های void و پیشنهادهای زنجیره‌ای؛ با محدودیت حداکثر ۱۰ نتیجه |
| CSS | `alfacode/src/language/css/css-completion.js` | `CSS_PROPERTIES`، `COMMON_VALUES`، `VALUE_CATALOG` و `DESCRIPTIONS`؛ خروجی `getCSSCompletionCatalog()` | پیشنهاد انتخابگر، ویژگی CSS یا مقدار متناسب با ویژگی جاری؛ تشخیص حضور مکان‌نما در comment/string |
| JavaScript | `alfacode/src/language/javascript/javascript-completion.js` | `KEYWORDS`، `GLOBALS`، `METHODS` و `SNIPPETS`؛ خروجی `getJavaScriptCompletionCatalog()` | کلمات کلیدی و نام‌های سراسری یا متدهای شناخته‌شده برای عضو پس از نقطه؛ تشخیص comment/string |

**جزئیات HTML:** رکوردهای پایه شامل نام تگ، رتبه، توضیح و در صورت نیاز ویژگی‌هایی مانند `void` و `contexts` هستند. داده SVG جداگانه تعریف شده و برخی عناصر زمینه‌ای مانند `caption`، `colgroup`، `tfoot`، `optgroup`، `dt` و `dd` از `CONTEXT_TAGS` به دست می‌آیند. API کاتالوگ فعلی فقط `category`، `label` و `description` را برمی‌گرداند؛ بنابراین همه جزئیات لازم برای اجرای موتور را به‌تنهایی صادر نمی‌کند.

**جزئیات CSS:** فهرست ویژگی‌ها، مقادیر عمومی و مقادیر مختص هر ویژگی منابع جداگانه‌اند. انتخابگرهای نمونه نیز داخل منطق موتور تعریف شده‌اند. API کاتالوگ این مجموعه‌ها را به ردیف‌های نمایشی `category`، `label` و `description` تبدیل می‌کند؛ نوع پیشنهاد و ارتباط مقدار با ویژگی در مدل فعلی کاتالوگ به‌صورت ساختاریافته حفظ نمی‌شود.

**جزئیات JavaScript:** کلمات کلیدی، شناسه‌های سراسری، متدهای هر شیء و snippetها در آرایه‌ها/آبجکت‌های مستقل تعریف شده‌اند. یک تفاوت مهم شناسایی شد: `SNIPPETS` در خروجی کاتالوگ نمایش داده می‌شوند، اما در مسیر فعلی `getJavaScriptCompletionSuggestions()` به‌عنوان گزینه قابل پذیرش وارد نمی‌شوند. بنابراین «قابل مشاهده بودن در جدول» الزاماً به معنی «قابل پیشنهاد بودن در ویرایشگر» نیست.

**اتصال صفحه فعلی:** `core/completion-catalog/completion-catalog.js` سه API بالا را مستقیماً import و خروجی آن‌ها را در یک آرایه ترکیب می‌کند. صفحه در حال حاضر فقط فهرست، فیلتر زبان، جست‌وجو و شمارش را دارد؛ فرم ورود، پیش‌نویس، ویرایش رکورد یا انتشار GitHub در آن وجود ندارد.

**نتیجه معماری این ممیزی:** JSON مرکزی نباید صرفاً فهرستی از واژه و توضیح باشد. برای حفظ رفتار موتور، باید نوع رکورد و معنای عملیاتی آن را نیز مدل کند؛ از جمله زبان، شناسه پایدار، دسته‌بندی، label/keyword، متن درج، نوع پیشنهاد، رتبه یا ترتیب، و ویژگی‌های اختیاری مخصوص هر زبان مانند void/context، مقادیر وابسته به property، owner متد و snippet. جزئیات دقیق و فیلدهای نهایی در زیرمرحله ۱-۲ و schema نهایی در ۱-۳ تعیین می‌شوند. تا آن زمان هیچ داده‌ای به JSON منتقل نمی‌شود.


### گزارش ممیزی عمیق مرحله ۱-۲ — ساختار، context و وابستگی موتورهای تکمیل

این بررسی بر پایه سورس فعلی انجام شد. در این زیرمرحله هیچ کد اجرایی یا داده‌ای تغییر نکرده است.

#### HTML
- داده‌های پایه در `HTML_TAG_CATALOG` شامل `name`، `rank`، `description` و ویژگی‌های اختیاری `void` و `contexts` هستند. مجموعه‌های جداگانه `SVG_TAGS`، `HEAD_TAGS`، `PHRASING_TAGS` و `CONTEXT_TAGS` رفتار پیشنهاد را تکمیل می‌کنند.
- وابستگی اجرایی: `html-completion.js` به `html-rules.js` برای تشخیص عناصر void و به `html-parser.js` برای تشخیص محدوده‌هایی که پیشنهاد نباید نمایش داده شود وابسته است.
- context از stack تگ‌های باز استخراج می‌شود. والدهایی مانند `ul`، `ol`، `table`، `tr`، `select` و `optgroup` فهرست فرزند محدود دارند؛ `head`، ریشه سند، محتوای `p` و محیط SVG نیز مسیرهای ویژه دارند. پیشنهاد تگ بسته‌شونده از stack بازها می‌آید و پیشنهاد زنجیره‌ای شامل فرزندان زمینه و در صورت یافتن تگ بسته، گزینه پرش به آن است.
- هر پیشنهاد اجرایی باید حداقل نوع عملیات (`open`، `close`، `child` یا `jump-close`)، محدوده جایگزینی، نام تگ و برای درج باز، وضعیت void را حفظ کند. `rank` ترتیب گزینه‌های باز را تعیین می‌کند؛ ترتیب close از نزدیک‌ترین والد به بیرون است.
- محدودیت ممیزی: قواعد context مجموعه‌ای دستی و ناقص نسبت به content model کامل HTML هستند. stack scanner نیز یک تحلیلگر سبک است و تمام قواعد اصلاح خودکار درخت HTML، تگ‌های اختیاری و مدل محتوا را پیاده نمی‌کند. تشخیص برخی contextها بر اساس نام والد و اسکن متن انجام می‌شود، نه AST کامل.

#### CSS
- داده‌ها به چهار گروه معنایی جدا تقسیم شده‌اند: `CSS_PROPERTIES`، `COMMON_VALUES`، `VALUE_CATALOG` با کلید نام property و `DESCRIPTIONS`. انتخابگرهای نمونه نیز در بدنه موتور تعریف شده‌اند.
- سه mode اجرایی وجود دارد: `selector`، `property` و `value`. پیشنهاد مقدار وابسته به نام property جاری است؛ بنابراین مقدارها را نمی‌توان بدون کلید مالک/property به یک فهرست تخت تبدیل کرد.
- وابستگی اجرایی فعلی به parser یا قواعد CSS واردشده در فایل `css-completion.js` وجود ندارد؛ تشخیص mode با بررسی ساده آخرین آکولاد، آخرین نقطه‌ویرگول و دونقطه انجام می‌شود. `css-rules.js` در این موتور تکمیل import نشده است.
- هر پیشنهاد باید `kind`، `label`، `insertText)، محدوده جایگزینی و در حالت value، شناسه/نام property مالک را نگه دارد. دسته‌بندی نمایشی کاتالوگ به‌تنهایی این رابطه را بازنمایی نمی‌کند.
- محدودیت ممیزی: تحلیل comment/string و مرزبندی declarationها heuristic است؛ ساختارهای تو‌در‌تو، رشته‌ها و توابع پیچیده، custom properties و grammar کامل CSS به‌صورت parser-driven مدل نشده‌اند. فهرست مقادیر نیز پوشش جامع مشخصات CSS نیست.

#### JavaScript
- داده‌ها در `KEYWORDS`، `GLOBALS`، نگاشت `METHODS` بر اساس owner و نگاشت `SNIPPETS` قرار دارند.
- دو mode اجرایی وجود دارد: `identifier` برای کلیدواژه‌ها و globals و `member` برای متدهای شناخته‌شده پس از نقطه. فهرست متدها وابسته به owner است؛ برای مثال `console.log` و `Math.max` باید مالک خود را حفظ کنند.
- موتور تکمیل فعلی parser و tokenizer جاوااسکریپت را مصرف نمی‌کند؛ تشخیص زمینه با regex روی متن قبل از مکان‌نما و اسکن ساده comment/string انجام می‌شود. قواعد parser در `javascript-rules.js` به‌طور مستقیم در این موتور تکمیل استفاده نشده‌اند.
- تفاوت مهم تأیید شد: `SNIPPETS` فقط در کاتالوگ نمایش داده می‌شوند و در `getJavaScriptCompletionSuggestions()` گزینه قابل پذیرش تولید نمی‌کنند. بنابراین نباید آن‌ها را به‌عنوان completion فعال در JSON اولیه وارد موتور کرد، مگر آنکه رفتار جداگانه‌ای در مرحله اتصال طراحی و تأیید شود.
- محدودیت ممیزی: تشخیص member محدود به الگوی ساده `identifier.memberPrefix` است و زنجیره‌های پیچیده، optional chaining، computed members و تحلیل نوع/شناسه واقعی را پوشش نمی‌دهد. فهرست globals و methods نیز curated است، نه حاصل تحلیل محیط اجرا.

#### قرارداد مشترک خروجی و اتصال رابط
- خروجی‌های سه موتور هم‌شکل نیستند: HTML از `mode` و `context` به‌همراه kindهای عملیاتی تگ استفاده می‌کند؛ CSS modeهای selector/property/value دارد؛ JavaScript modeهای identifier/member دارد. در هر سه، `from` و `to` محدوده جایگزینی و `options` فهرست گزینه‌ها را تعیین می‌کنند، اما فیلدهای اختصاصی زبان متفاوت‌اند.
- رابط `core/editor/editor.js` موتور متناسب با تب فعال را فراخوانی می‌کند و سقف ۱۰ گزینه می‌فرستد. برای CSS/JavaScript درج با `insertText` و سپس `label` انجام می‌شود؛ HTML منطق درج جداگانه‌ای برای جفت تگ، void، close و jump دارد. این تفاوت باید در مدل داده حفظ شود و نباید یکسان‌سازی سطحی شود.
- APIهای کاتالوگ عمدتاً داده نمایشی `category`، `label` و `description` می‌دهند؛ این خروجی‌ها به‌تنهایی برای بازسازی رفتار پیشنهاد کافی نیستند. کاتالوگ HTML بعضی contextها را تخت می‌کند؛ کاتالوگ CSS ارتباط property/value را فقط در نام category متنی نشان می‌دهد؛ کاتالوگ JavaScript snippetهای غیرفعال در موتور را نیز نشان می‌دهد.
- اعتبارسنجی مکان‌نما و فیلترکردن موارد نامعتبر باید در لایه موتور باقی بماند؛ JSON مرجع باید داده‌های قابل‌پیکربندی را نگه دارد و نباید منطق اجرایی یا کد قابل اجرا ذخیره کند.

#### نتیجه مرحله ۱-۲ و ورودی طراحی schema

برای schema مرحله ۱-۳ باید یک envelope مشترک نسخه‌دار همراه با رکوردهای زبان‌محور در نظر گرفته شود. فیلدهای مشترک پیشنهادی برای بررسی در طراحی نهایی: شناسه پایدار، زبان، دسته/گروه، label، description، نوع پیشنهاد، متن درج، وضعیت فعال، ترتیب/رتبه و trigger یا الگوی فعال‌سازی. فیلدهای اختصاصی باید ساختاریافته بمانند: HTML شامل نوع عملیات، void و context/parent؛ CSS شامل mode و property مالک برای valueها؛ JavaScript شامل mode و owner برای memberها. snippetها باید از گزینه‌های فعال جدا یا با وضعیت صریح غیرفعال مدل شوند.

**وضعیت:** ممیزی ساختار و وابستگی‌های فعلی تکمیل شد؛ هیچ داده‌ای منتقل و هیچ رفتار موتوری تغییر نکرد. مرحله بعد فقط طراحی schema نهایی در زیرمرحله ۱-۳ است و به تأیید مدیر پروژه نیاز دارد.

### طراحی نهایی قرارداد داده JSON — زیرمرحله ۱-۳

این قرارداد برای انتقال داده‌های قابل پیکربندی پیشنهادها به یک منبع مرجع مشترک طراحی شده است. نسخه نخست در مسیر برنامه‌ریزی‌شده `alfacode/data/completions.json` قرار خواهد گرفت؛ در این زیرمرحله فقط قرارداد مستند شده و فایل داده ساخته نشده است.

#### ۱. Envelope و نسخه‌بندی

ریشه JSON از این ساختار مفهومی پیروی می‌کند:

```json
{
  "schemaVersion": 1,
  "catalogVersion": 1,
  "records": []
}
```

- `schemaVersion` نسخه ساختار و قواعد اعتبارسنجی است؛ تغییر ناسازگار در شکل/معنای فیلدها آن را افزایش می‌دهد.
- `catalogVersion` نسخه محتوای کاتالوگ است و با هر انتشار محتوایی افزایش می‌یابد؛ الزاماً با نسخه schema یکی نیست.
- `records` آرایه رکوردهای typed است. هر رکورد دقیقاً یک زبان و یک نوع معنایی مشخص دارد.
- فیلد ناشناخته در نسخه schema جاری باید در اعتبارسنجی رد شود، مگر آنکه در نسخه‌های بعدی صریحاً به‌عنوان extension مجاز تعریف شود. فیلد اختیاریِ غایب با مقدار خالی یا null بی‌دلیل جایگزین نمی‌شود.

#### ۲. فیلدهای مشترک رکورد

| فیلد | نوع | الزام و معنا |
|---|---|---|
| `id` | string | اجباری؛ شناسه پایدار و یکتا در کل کاتالوگ، مستقل از label |
| `language` | enum | اجباری؛ یکی از `html`، `css`، `javascript` |
| `type` | string | اجباری؛ نوع معنایی رکورد که با زبان محدودتر می‌شود |
| `category` | string | اجباری؛ گروه نمایشی کاتالوگ |
| `label` | string | اجباری؛ متن نمایشی گزینه |
| `description` | string | اختیاری؛ توضیح کوتاه |
| `insertText` | string | اختیاری و فقط برای مواردی که موتور از درج متنی استفاده می‌کند |
| `rank` | integer | اختیاری؛ رتبه عددی کمتر، اولویت بالاتر؛ فقط جایی که ترتیب رتبه‌ای معنا دارد |
| `order` | integer | اختیاری؛ ترتیب پایدار نمایش در گروه‌هایی که رتبه معنایی ندارند |
| `enabled` | boolean | اجباری؛ فعال بودن برای موتور پیشنهاد؛ مقدار false به معنی نمایش احتمالی در کاتالوگ بدون پیشنهاد فعال است |
| `trigger` | object | اختیاری؛ توصیف داده‌ای trigger/prefix در صورت نیاز؛ بدون regex اجرایی یا کد |

شناسه‌ها پس از ایجاد نباید با تغییر label یا دسته‌بندی عوض شوند. تکرار `id` ممنوع است. یکتایی معنایی بر اساس زبان، نوع، مالک و کلید آیتم نیز در validator بررسی می‌شود؛ زیرا یک label می‌تواند در context یا مالک متفاوت معتبر باشد.

#### ۳. داده‌های اختصاصی HTML

رکوردهای HTML از `language: "html"` استفاده می‌کنند و فیلدهای اختصاصی زیر را دارند:

- `tagName`: نام canonical تگ؛ برای تشخیص و درج موتور.
- `operation`: یکی از `open`، `close`، `child` یا `jump-close`. رکوردهای catalog-only می‌توانند `catalog` داشته باشند و نباید به‌عنوان گزینه اجرایی تلقی شوند.
- `isVoid`: boolean؛ برای رکوردهای تگ باز اجباری و مطابق قواعد HTML؛ برای تگ void درج تگ پایانی ممنوع است.
- `contexts`: آرایه contextهای مجاز مانند `root`، `head`، `body` یا contextهای اختصاصی موجود؛ این فیلد داده زمینه‌ای است، نه ادعای پیاده‌سازی کامل content model استاندارد.
- `parentTags`: آرایه نام والدهای مجاز، فقط برای قواعدی که محدودیت والد مشخص دارند.
- `namespace`: یکی از `html` یا `svg` تا عناصر SVG با HTML معمولی مخلوط نشوند.

محدوده جایگزینی `from/to` و موقعیت مکان‌نما، نتیجه تحلیل متن جاری‌اند و در JSON ذخیره نمی‌شوند. رفتار جفت‌سازی تگ، stack، تشخیص تگ بسته موجود و پرش به آن همچنان مسئولیت موتور است؛ رکورد داده نباید الگوریتم یا عبارت اجرایی برای این رفتار داشته باشد. `rank` برای ترتیب گزینه‌های باز به‌کار می‌رود؛ ترتیب close همچنان از stack زمان اجرا می‌آید.

#### ۴. داده‌های اختصاصی CSS

رکوردهای CSS از `language: "css"` استفاده می‌کنند:

- `mode`: یکی از `selector`، `property` یا `value`.
- `propertyName`: برای رکوردهای `value` اجباری و برای سایر modeها غایب؛ نام property مالک مقدار.
- `insertText`: برای پیشنهادهای قابل پذیرش اجباری؛ رشته‌ای که موتور در سند درج می‌کند.
- `label`: متن نمایشی؛ می‌تواند با `insertText` متفاوت باشد.

مقادیر عمومی نیز می‌توانند به‌صورت رکوردهای value با مالک صریحِ گروه عمومی (در نسخه قرارداد: `propertyName: "*"`) مدل شوند؛ موتور هنگام پیشنهاد مقدار، ابتدا مقادیر property جاری و سپس مقادیر عمومی را ترکیب و تکراری‌ها را حذف می‌کند. انتخابگرهای نمونه با `mode: "selector"` نگهداری می‌شوند. تشخیص mode و property جاری همچنان در موتور است و JSON فقط گزینه‌ها را توصیف می‌کند.

#### ۵. داده‌های اختصاصی JavaScript

رکوردهای JavaScript از `language: "javascript"` استفاده می‌کنند:

- `mode`: یکی از `identifier` یا `member`؛ برای snippetهای غیرفعال `snippet`.
- `owner`: برای `member` اجباری؛ نام شیء/مالک مانند `console` یا `Math`. برای identifier غایب.
- `insertText`: برای پیشنهاد فعال اجباری.
- `enabled`: رکوردهای کلیدواژه، global و member قابل پیشنهاد باید true باشند. snippetهای فعلی چون در مسیر پیشنهاد قابل پذیرش نیستند باید `enabled: false` و `mode: "snippet"` داشته باشند تا حضورشان در کاتالوگ با فعال بودن در موتور اشتباه نشود.

این schema به‌تنهایی snippet expansion را فعال نمی‌کند. فعال‌سازی snippetها نیازمند تصمیم و پیاده‌سازی مستقل در مرحله اتصال موتور است.

#### ۶. مرز داده و منطق اجرایی

JSON فقط داده ساده و قابل اعتبارسنجی نگه می‌دارد. ذخیره JavaScript، function، callback، expression قابل اجرا، `eval`، regex اجرایی یا منطق parser در آن ممنوع است. Triggerها، contextها و نوع عملیات فقط با enumها و مقادیر داده‌ای محدود بیان می‌شوند. محاسبه context، فیلتر، رتبه‌بندی نهایی، محاسبه محدوده درج، مدیریت stack و اعمال transaction در موتورهای موجود باقی می‌ماند.

#### ۷. سازگاری و مهاجرت

در مرحله ۲، داده اولیه از منابع واقعی فعلی استخراج می‌شود و باید با خروجی و رفتار فعلی موتور مقایسه شود. در مرحله ۷ اتصال مصرف‌کننده‌ها به JSON به‌صورت تدریجی انجام می‌شود؛ تا زمان تکمیل و آزمون هر زبان، منبع فعلی آن زبان حذف نمی‌شود. adapter هر زبان باید قرارداد خروجی کنونی موتور را حفظ کند: `mode`، `context` در HTML، `from/to`، `options`، `kind` و `insertText` در موارد مربوط. محدودیت‌های فعلی context و parser نیز با انتقال داده به‌طور خودکار برطرف‌شده تلقی نمی‌شوند.

#### ۸. قواعد اعتبارسنجی اولیه

- اعتبارسنجی نوع و نسخه envelope و آرایه records.
- یکتایی `id` و عدم تکرار کلید معنایی هر زبان.
- enumهای محدود برای language، type، operation، namespace و mode.
- الزام فیلدهای وابسته: HTML برای tagName/operation و void؛ CSS برای propertyName در value؛ JavaScript برای owner در member.
- رد insertText خالی برای پیشنهاد فعال؛ رد رکورد فعال snippet تا زمانی که پشتیبانی اجرایی آن تصویب و پیاده‌سازی نشده باشد.
- بررسی سازگاری تگ‌های void و namespace؛ بررسی نبود owner برای رکوردهای نامرتبط.
- رد هر مقدار غیر داده‌ای یا هرگونه کد اجرایی.

**وضعیت زیرمرحله ۱-۳:** طراحی schema نهایی و قواعد سازگاری مستند شد. هیچ JSON، validator، UI یا کد اجرایی ایجاد/تغییر نکرد و تستی اجرا نشد. مرحله بعد ۲-۱، استخراج JSON اولیه از داده‌های واقعی موجود است و فقط پس از تأیید مدیر پروژه آغاز می‌شود.
